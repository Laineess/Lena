## 1. Qué se despliega hoy

**Solo Postgres.** El API y la PWA no existen todavía (fase 2 y 4 del cronograma).

Parece prematuro y no lo es: la tarea 0.7 del cronograma dice **desplegar en la semana 1 aunque no haya nada que desplegar**. Un despliegue que se construye al final se construye con prisa y se rompe el día del lanzamiento. Hacerlo ahora, con una sola pieza, significa que las ~700 horas siguientes llegan a producción sin drama.

## 3. Endurecer el servidor (RS-T-5, RS-T-12)

Antes de instalar nada. Un Postgres bien configurado en un servidor abierto no sirve de nada.

```bash
# Actualizar
sudo apt update && sudo apt upgrade -y

# Actualizaciones de seguridad automáticas (RS-T-12)
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
```

### 3.1 Usuario sin privilegios

Nunca operar como `root`:

```bash
sudo adduser lena
sudo usermod -aG sudo lena
```

Copia tu llave SSH desde **tu máquina**:

```bash
ssh-copy-id lena@TU_IP
```

Verifica que entras **antes** de seguir. El siguiente paso te deja fuera si te equivocas.

### 3.2 SSH: solo llave, sin root (RS-T-5)

```bash
sudo nano /etc/ssh/sshd_config
```

```
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
```

```bash
sudo systemctl restart ssh
```

> ⚠️ **Deja tu sesión actual abierta** y prueba entrar desde otra terminal antes de cerrarla. Si `PasswordAuthentication no` queda mal configurado y tu llave falla, pierdes el acceso al servidor.

### 3.3 Firewall (RS-T-5)

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 443/tcp        # para la fase 2
sudo ufw enable
sudo ufw status
```

**El 5432 NO se abre.** Postgres no se expone jamás (RS-T-6). Si necesitas conectarte desde tu máquina, se hace por túnel SSH (§7), no abriendo el puerto.

### 3.4 fail2ban

```bash
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban
```

## 4. Docker

```bash
# Repositorio oficial de Docker
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin

# Correr docker sin sudo
sudo usermod -aG docker $USER
newgrp docker

docker --version
docker compose version
```

**No uses el `docker.io` de Ubuntu:** va atrasado y trae una versión vieja de Compose.

## 6. Levantar la base

```bash
docker compose up -d postgres
docker compose ps
docker compose logs postgres | tail -20
```

Debe decir `database system is ready to accept connections`.

### 6.1 Migraciones

Necesitas Node en el VPS (solo para migrar y respaldar):

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
sudo npm install -g pnpm

cd /opt/lena
pnpm install --prod=false
pnpm db:migrate
```

### 6.2 Fijar la contraseña del rol de la aplicación

La migración `0001` crea `lena_app` con una contraseña marcador. **Cámbiala:**

```bash
docker compose exec postgres psql -U lena -d lena \
  -c "ALTER ROLE lena_app WITH PASSWORD '<la que pusiste en DATABASE_URL_APP>';"
```

### 6.3 Verificar el control antifraude

**Este es el paso que no hay que saltarse.** Comprueba que el log es append-only de verdad (RS-U-1, T1):

```bash
docker compose exec postgres psql -U lena -d lena -c "
  SELECT grantee, privilege_type
  FROM information_schema.role_table_grants
  WHERE table_name = 'comanda_evento' AND grantee = 'lena_app';"
```

Debe listar **`SELECT` e `INSERT`, y NADA más**. Si aparece `UPDATE` o `DELETE`, el control antifraude no existe.

Prueba real, conectándote como la aplicación:

```bash
docker compose exec postgres psql -U lena_app -d lena \
  -c "DELETE FROM comanda_evento;"
```

**Debe fallar con `ERROR: permission denied`.** Si borra filas, algo está mal: probablemente el API está conectando como dueño, y entonces el "log inmutable" es solo una convención que cualquier endpoint puede romper.

## 7. Conectarte desde tu máquina (sin abrir puertos)

El 5432 nunca se expone (RS-T-6). Túnel SSH:

```bash
ssh -L 5433:localhost:5432 lena@TU_IP
```

Mientras la sesión esté abierta, tu máquina ve la base del VPS en `localhost:5433`:

```bash
DATABASE_URL=postgresql://lena:<pass>@localhost:5433/lena pnpm db:studio
```

**El túnel cifra y autentica con tu llave SSH.** Abrir el 5432 al internet expondría Postgres a los escaneos automáticos que corren todo el día contra cualquier IP pública.

## 8. Respaldos (RS-T-14, RNF-D-5)

```bash
sudo mkdir -p /opt/lena/backups
sudo chown $USER:$USER /opt/lena/backups
nano /opt/lena/scripts/backup.sh
```

```bash
#!/usr/bin/env bash
# Respaldo diario. RS-T-14: cifrado, fuera del VPS, retención 30 días.
set -euo pipefail

cd /opt/lena
source .env

FECHA=$(date +%Y%m%d_%H%M%S)
ARCHIVO="/opt/lena/backups/lena_${FECHA}.sql.gz"

docker compose exec -T postgres \
  pg_dump -U "${POSTGRES_USER}" -d "${POSTGRES_DB}" --clean --if-exists \
  | gzip > "${ARCHIVO}"

# Retención 30 días
find /opt/lena/backups -name 'lena_*.sql.gz' -mtime +30 -delete

# El respaldo debe salir del VPS: si el disco muere, se lleva los respaldos.
# rclone copy "${ARCHIVO}" remoto:lena-backups/

echo "$(date -Is) OK ${ARCHIVO} ($(du -h "${ARCHIVO}" | cut -f1))"
```

```bash
chmod +x /opt/lena/scripts/backup.sh
crontab -e
```

```
0 4 * * * /opt/lena/scripts/backup.sh >> /opt/lena/backups/backup.log 2>&1
```

**Las 4 AM son a propósito:** la taquería ya cerró y no hay nadie capturando.

### 8.1 Restaurar — el paso que la gente omite (RS-T-15)

```bash
gunzip -c /opt/lena/backups/lena_XXXX.sql.gz \
  | docker compose exec -T postgres psql -U lena -d lena
```

**Un respaldo que nunca se restauró es una hipótesis, no un respaldo.** RNF-D-6 exige un simulacro trimestral. El día que lo necesites no es el día de averiguar si funciona.

### 8.2 Sobre el RPO

RNF-D-7 tolera perder 24 h **en el servidor**, y suena mal hasta que se ve la letra chica: **el RPO en los dispositivos es cero.** Los eventos siguen en la outbox de cada tablet hasta que el servidor los confirma. Restaurar un respaldo de ayer **no pierde las comandas de hoy** — las tablets las vuelven a empujar solas.

Es una propiedad emergente del diseño offline-first (ADR-005), no un componente aparte.

## 9. Operación diaria

| Qué | Comando |
|---|---|
| Estado | `docker compose ps` |
| Logs | `docker compose logs -f postgres` |
| Actualizar | `git pull && pnpm install && pnpm db:migrate` |
| Reiniciar | `docker compose restart postgres` |
| Espacio en disco | `df -h && docker system df` |

**Nunca** `docker compose down -v` en producción: la `-v` borra el volumen, y con él la base entera.

## 11. Fase 3 del producto — nodo de sucursal (ADR-004 Nivel 2)

Cuando llegue, **este mismo `docker-compose.yml` corre en el mini PC de la sucursal**. Misma imagen, mismo protocolo de sync. Las tablets solo cambian de URL base.

**Que sea así es la justificación entera de haber elegido VPS propio sobre Supabase** (ADR-001): es un cambio de despliegue, no un rewrite.

**Su disparador es una métrica, no una fecha** (`06` §10.1): si "comandas creadas offline" supera el 10%, el internet de la sucursal es peor de lo esperado y esto deja de ser fase 3 para volverse urgente.
