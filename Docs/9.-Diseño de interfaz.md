## 1. Principios

Cinco reglas. Ante cualquier duda de diseño, se resuelve con estas.

| # | Principio | Consecuencia |
|---|---|---|
| **D1** | **El color es información, no decoración.** | La marca vive en acentos. Verde/ámbar/rojo significan **estado** y nunca se usan por bonito |
| **D2** | **El mesero nunca espera.** | Escritura optimista. La UI responde en < 100 ms sin importar la red (RNF-P-1) |
| **D3** | **Nunca mentir sobre la conexión.** | El estado de sync es permanente y honesto (RF-E-14, RF-J-4) |
| **D4** | **Cocina se lee a metro y medio, con las manos sucias.** | Texto ≥ 32 px (9.1 mm), objetivos ≥ 88 px, un solo botón por tarjeta |
| **D5** | **Cancelar cuesta dinero y hay que decirlo.** | Toda cancelación muestra el costo antes de confirmar (RF-E-18) |
| **D6** | **El lienzo es de 400 × 670 CSS.** | Lo que no quepa ahí no existe. **Es la restricción que manda sobre todas las demás** |

**D1 tiene una consecuencia dura en la pantalla de cocina: ahí la marca no aparece.** Si el naranja de "Leña" y el naranja de "esta comanda lleva 7 minutos" conviven, el segundo deja de gritar. En cocina el único color es el estado.

**D6 es el principio que más decisiones tomó, y llegó tarde.** La Galaxy Tab A11 tiene `devicePixelRatio` = 2.0: sus 1340 × 800 físicos se traducen a **400 × 670 CSS en vertical** y **670 × 400 en horizontal**. Eso es un lienzo más chico que un teléfono en horizontal.

**La buena noticia del `dpr` 2.0 es que los milímetros sobran** (1 px CSS = 0.284 mm): el texto y los botones son físicamente generosos sin esfuerzo. **La mala es que los píxeles escasean.** El diseño no pelea por legibilidad — pelea por espacio.

## 2. Sistema de diseño

### 2.1 Color — escala Brasa

La marca es una escala completa, no un color suelto. Cada tono tiene su trabajo.

| Token | Hex | Uso |
|---|---|---|
| `brasa-50` | `#FFF7ED` | Fondo de aviso, selección suave |
| `brasa-100` | `#FFEDD5` | Fondo de categoría activa |
| `brasa-200` | `#FED7AA` | Bordes suaves |
| `brasa-300` | `#FDBA74` | — |
| `brasa-400` | `#FB923C` | Acento en tema oscuro |
| `brasa-500` | `#F97316` | Iconos decorativos |
| `brasa-600` | `#EA580C` | Hover del botón primario |
| **`brasa-700`** | **`#C2410C`** | **Botón primario, logo, enlaces** |
| `brasa-800` | `#9A3412` | Presionado |
| `brasa-900` | `#7C2D12` | — |
| `brasa-950` | `#431407` | — |

`brasa-700` sobre blanco da **6.0:1** → AA para texto normal, AAA para texto grande. Es el tono más saturado que aún permite texto encima sin pelear.

### 2.2 Color — neutros Piedra

Warm gray. Un gris azulado junto a una marca naranja se ve sucio; el warm gray la acompaña.

| Token | Hex | Uso |
|---|---|---|
| `piedra-50` | `#FAFAF9` | Fondo de app (claro) |
| `piedra-100` | `#F5F5F4` | Fondo hundido |
| `piedra-200` | `#E7E5E4` | Bordes, separadores |
| `piedra-300` | `#D6D3D1` | Bordes de control |
| `piedra-400` | `#A8A29E` | Texto deshabilitado |
| `piedra-500` | `#78716C` | Texto secundario — 5.3:1 ✓ |
| `piedra-600` | `#57534E` | Iconos |
| `piedra-700` | `#44403C` | Superficie (oscuro) |
| `piedra-800` | `#292524` | Tarjeta (oscuro) |
| `piedra-900` | `#1C1917` | Texto principal / fondo oscuro |
| `piedra-950` | `#0C0A09` | Fondo hundido (oscuro) |

`piedra-900` sobre `piedra-50` = **16.1:1** → AAA.

### 2.3 Color — estado

**Estos son los únicos colores que gritan.**

| Significado | Claro | Oscuro | Contraste |
|---|---|---|---|
| En línea, confirmado, listo | `#15803D` | `#4ADE80` | 4.9:1 / 9.4:1 ✓ |
| Pendiente, atención | `#A16207` | `#FACC15` | 4.6:1 / 11.6:1 ✓ |
| Sin red, urgente, error | `#B91C1C` | `#F87171` | 6.4:1 / 7.4:1 ✓ |
| Informativo | `#1D4ED8` | `#60A5FA` | 7.0:1 / 6.9:1 ✓ |

**Ningún estado se comunica solo con color** (WCAG 1.4.1). Siempre color **+** icono **+** texto. Un cocinero daltónico existe, y una pantalla con grasa también.

### 2.3b Color — escritorio de gestión (tema oscuro, v1.1)

Solo para el escritorio del superadmin/administrador (§7). El POS sigue claro.

| Token | Uso | Ejemplo |
|---|---|---|
| `carbon-950 / 900 / 850 / 800` | Fondos: página, barra lateral, tarjetas, hover | `#0a0a0b` … `#1e1e22` |
| `carbon-700 / 600` | Bordes y separadores | `#2a2a30` / `#3a3a42` |
| `rojo-600 / 500` | Acción primaria (Crear/Guardar) y destructiva; barras | `#d1373c` / `#e5484d` |
| `rojo-400` | Alertas, merma, cifras en rojo | `#f26d6d` |
| `oro-400 / 300` | Detalles: logo, títulos de tarjeta, cifras KPI, enlaces | `#d9b44a` / `#ecd28a` |

Negro primario, rojo secundario, dorado para el detalle. El rojo se reserva para lo
que exige acción o atención (igual que el estado "error" del POS); el dorado da el
acento de marca sin gritar.

### 2.4 Tipografía

**Inter** en toda la aplicación. Un solo tipo.

**Por qué Inter y no una fuente "de restaurante":** un POS necesita **cifras tabulares**. Sin `tabular-nums`, un cronómetro que pasa de `1:19` a `1:20` cambia de ancho y **baila**, y una columna de precios no alinea. Inter trae tabulares de fábrica, es variable (un archivo, todos los pesos) y está diseñada para pantallas pequeñas. Una serif de menú como Playfair es preciosa en una carta impresa e ilegible a metro y medio en una cocina.

```css
font-family: 'Inter var', system-ui, sans-serif;
/* Obligatorio en precios, totales, cronómetros y folios: */
font-variant-numeric: tabular-nums;
```

| Token | Tamaño / interlineado | Peso | Físico | Uso |
|---|---|---|---|---|
| `display` | 40 / 44 | 700 | 11.4 mm | Total a cobrar |
| `h1` | 26 / 32 | 700 | 7.4 mm | Título de pantalla |
| `h2` | 20 / 28 | 600 | 5.7 mm | Sección |
| `cocina-lg` | **32 / 40** | 700 | **9.1 mm** | **Producto en cocina** |
| `cocina-md` | 20 / 26 | 500 | 5.7 mm | **Nota en cocina** |
| `body` | 16 / 24 | 400 | 4.5 mm | Base |
| `body-lg` | 18 / 26 | 400 | 5.1 mm | Listas táctiles |
| `label` | 14 / 20 | 500 | 4.0 mm | Etiquetas |
| `caption` | 12 / 16 | 400 | 3.4 mm | Metadatos. **Prohibido para datos operativos** |

**`cocina-lg` a 32 px es un requisito funcional, no una preferencia** (RNF-U-5, D4): 32 px CSS × `dpr` 2.0 = 64 px físicos = **9.1 mm**, que se lee a **1.8 m** con margen sobre el metro y medio del montaje.

**La columna "Físico" existe porque los píxeles CSS mienten sobre el tamaño real**, y en este dispositivo mienten a favor: con `dpr` 2.0, cada px CSS son 0.284 mm — un 8% **más grande** que la referencia de 96 dpi. Un `body` de 16 px aquí mide 4.5 mm, más que en un monitor de escritorio.

**Por eso `cocina-lg` pudo subir de 24 a 32 px en vez de bajar.** La versión anterior de este documento asumía `dpr` 1.0-1.5 y concluía que había que montar la tablet a 70 cm para que se leyera. **Con el número real la conclusión se invierte:** sobra tamaño físico y lo que falta es lienzo.

### 2.5 Espaciado, radios, sombras

Escala de 4 px: `1=4 · 2=8 · 3=12 · 4=16 · 6=24 · 8=32 · 12=48 · 16=64`.

| Radio | Valor | Uso |
|---|---|---|
| `sm` | 6 px | Chips |
| `md` | 10 px | Botones, campos |
| `lg` | 14 px | Tarjetas |
| `full` | 9999 px | Botón circular de cocina |

Sombras suaves y escasas (`sm`, `md`, `lg`). En tema oscuro **no hay sombras**: la jerarquía se hace con superficie y borde, porque una sombra negra sobre fondo negro no existe.

### 2.6 Objetivos táctiles

| Contexto | CSS | Físico | Mínimo Android |
|---|---|---|---|
| General (RNF-U-3) | 48 × 48 px | **13.6 mm** | 9 mm ✓ |
| Steppers `[−] [+]` de captura | 56 × 56 px | 15.9 mm | 9 mm ✓ |
| Botón ✓ de cocina | **88 × 88 px** | **25.0 mm** | 9 mm ✓ |
| Separación entre objetivos | ≥ 8 px | 2.3 mm | 2 mm ✓ |

**Todo cumple con holgura, y no por generosidad de diseño sino por el `dpr` 2.0.** A 0.284 mm por px CSS, el mínimo de 48 px de Material Design da 13.6 mm — un 50% arriba del mínimo de 9 mm.

**Ese margen es el que financia el resto del diseño.** Como los objetivos táctiles sobran de tamaño físico, se pueden mantener en 48 px CSS sin culpa y gastar los píxeles ahorrados en lo que sí escasea: espacio de lista y ancho de tarjeta.

**El botón ✓ de cocina va a 88 px (25 mm)** porque ahí sí conviene exagerar: se toca con el dorso del dedo, de reojo, con prisa y con las manos grasosas.

```
│  ───────────────────────── │

├────────────────────────────┤

│ │  ENVIAR A COCINA  →    │ │ ← 64
│ └────────────────────────┘ │
└────────────────────────────┘

```

**Vertical y no horizontal, por una razón de aritmética** (RNF-C-7):

| | Vertical 400×670 | Horizontal 670×400 |
|---|---|---|
| Alto útil tras encabezado, pestañas y pie | **478 px** | 208 px |
| Productos visibles | **6-7** | 2-3 |

**En horizontal el mesero viviría haciendo scroll en hora pico.** Y de paso, vertical es como se carga una tablet caminando: con una mano, como libreta. El requisito RNF-U-4 ("operable con una mano") sale gratis con la orientación correcta.

**Cómo cumple los requisitos:**

| Requisito | Cómo |
|---|---|
| RNF-U-2 (≤ 2 toques) | `+` es **1 toque**. La cantidad se ve sin abrir nada |
| RNF-U-4 | Vertical, una mano. La columna de steppers va a la derecha, al alcance del pulgar |
| RF-D-7 | "Chorizo NO DISPONIBLE": atenuado y sin steppers |
| RF-E-3 | Toque largo sobre el renglón → hoja de notas |
| RF-E-10 | El precio mostrado es el que se **copia** a la línea |
| D3 | "● En línea" siempre visible arriba |
| D6 | Todo cabe en 400 px de ancho |

**Las pestañas de categoría llevan `›` al final** porque en 400 px no caben las cuatro. Sin esa pista, "Postres" no existiría para el mesero. Es el mismo problema del asomo de la cuarta tarjeta en cocina (§6.0): **en un lienzo chico, lo que no se ve hay que anunciarlo.**

**Los productos con cantidad > 0 se anclan arriba de la lista.** Lo que ya se pidió importa más que lo que falta por pedir, y evita que el mesero pierda de vista lo capturado al bajar la lista.

**"NO DISPONIBLE" ocupa el lugar del producto en vez de ocultarlo.** Si el pastor desapareciera de la lista, el mesero lo buscaría, no lo encontraría y creería que la app falla. Verlo tachado responde la pregunta antes de que la haga.

### 4.2 El identificador para vocear — el problema del "para llevar"

Al cliente de mostrador hay que gritarle algo. Pero **el folio lo asigna el servidor al sincronizar** (RF-E-13, ADR-003) y sin red no hay folio.

**Solución: cada dispositivo tiene una letra, y el ID local es letra + consecutivo.**

```
Tablet de Carlos → A-1, A-2, A-3 …
Tablet de Ana    → B-1, B-2, B-3 …
```

```
┌───────────────────────────────────┐
│         PARA LLEVAR               │
│                                   │
│            A-7                    │  ← 72 px. Esto se vocea
│                                   │
│   Folio #43 · confirmada          │  ← 12 px. Administrativo
└───────────────────────────────────┘
```

**Nunca colisiona** (la letra del dispositivo lo garantiza), funciona sin red y se grita fácil.

**Y el cliente jamás ve el folio.** Son dos identificadores con dos públicos: `A-7` es para la persona, `#43` es para la contabilidad. Enseñar los dos al cliente sería confundirlo; enseñar solo el folio sería imposible offline. **El ID que se vocea nunca cambia**, sincronice cuando sincronice.

```
└─────────────────────────────────────────────────────────────┘
```

**El cambio es lo más grande de la pantalla después del total.** Es el número que el mesero necesita **ya**, contando billetes frente al cliente. Enterrarlo en 14 px sería diseñar contra el trabajo real.

**Los atajos de $100/$200/$500 eliminan el error más común:** teclear el monto recibido. En una taquería el 90% de los pagos son con billete cerrado.

**Pago dividido (RF-G-3):** al elegir un segundo método se agrega un renglón. El botón `COBRAR` permanece **deshabilitado** hasta que `pagado = total` (RF-G-6), y la barra dice cuánto falta. La regla se muestra antes de romperse, no como error después.

Si nada se había enviado a cocina, el diálogo **no muestra merma** y solo pide motivo (RF-E-20).

### 6.0 Presupuesto de espacio — por qué son 2 tarjetas y no 3

El lienzo es de **670 × 400 CSS** (D6). Este es el reparto:

| Ancho | px |
|---|---|
| Márgenes | 16 |
| **Tarjeta × 2** | **310** c/u |
| Separación | 10 |
| **Asomo de la 3ª** | **24** |

| Alto | px |
|---|---|
| Encabezado | 40 |
| **Tarjeta** | **344** |
| Márgenes | 16 |

Y el contenido de una tarjeta de 310 × 344:

| Elemento | px |
|---|---|
| Borde superior de color | 8 |
| Cronómetro (32 px) | 40 |
| Folio + tipo (20 px) | 28 |
| Separador | 8 |
| Producto × 3 (32 px) | 120 |
| Botón ✓ | 88 |
| Padding | 32 |
| **Total** | **324** de 344 ✓ |

**Por qué 2 y no 3, que era lo pedido:** a 3 tarjetas el ancho cae a ~206 px, y ahí `2× QUESO FUNDIDO` a 32 px (~304 px de ancho) **no cabe en un renglón**. Habría que partirlo en dos o bajar el texto a 24 px. **A 310 px cabe entero.**

**El intercambio es honesto y hay que verlo de frente:** se ven 2 comandas en vez de 3 sin deslizar. Pero el cocinero trabaja **la de la izquierda** — la más vieja — y la segunda es la que sigue. Ver la tercera de un vistazo vale menos que leer bien las dos que importan.

**El asomo de la tercera tarjeta no es estética.** Sin ese borde visible no hay ninguna pista de que hay más comandas a la derecha, y un cocinero jamás va a deslizar una pantalla que parece completa. **24 píxeles que evitan que se pierdan comandas.**

**Lo que se fue para que quepa:**

| Recorte | Por qué es aceptable |
|---|---|
| Logo de marca | D1: en cocina el color y el espacio son solo información |
| Tercera tarjeta completa | Se anuncia con el asomo. El trabajo real está en la primera |
| Aire y márgenes | Adorno |

**Nada de lo recortado toca la legibilidad ni el objetivo táctil**, que es justo lo contrario de lo que este documento planteaba antes de conocer el `dpr` real. A 2.0, el texto de 32 px mide 9.1 mm y se lee a **1.8 m** — con margen sobre el metro y medio del montaje.

**Si una comanda tiene más de 3 líneas**, la tarjeta muestra las 3 primeras y `+2 más`, con scroll vertical dentro de la tarjeta. Es preferible a encoger el texto: una tarjeta ilegible no sirve de nada, una con scroll sí.

### 6.1 Color de tarjeta por tiempo (RF-F-7, RF-F-8)

| Tiempo | Relleno | Borde superior (8 px) | Chip |
|---|---|---|---|
| 0–2 min | `piedra-800` `#292524` | `piedra-600` | Gris |
| 2–5 min | `#854D0E` | `#FACC15` amarillo | 🟡 |
| 5–8 min | `#9A3412` | `#FB923C` naranja | 🟠 |
| > 8 min | `#991B1B` | `#F87171` rojo | 🔴 **pulsa** |

Umbrales configurables por sucursal (RF-F-8).

**El color se codifica tres veces —relleno, borde y chip— a propósito.** El relleno usa tonos oscuros (`800`/`900`) para que el **texto blanco se mantenga siempre**, en las cuatro etapas, arriba de 7:1 (AAA). Un relleno amarillo brillante obligaría a texto oscuro, y **el color del texto cambiaría con el tiempo** — un cocinero leyendo texto negro en una tarjeta y blanco en la de al lado.

Pero un relleno oscuro solo no grita a metro y medio. Por eso el **borde superior de 8 px lleva el tono brillante**: ese es el que se ve desde la plancha. Relleno legible + borde visible + chip redundante. Y funciona para un cocinero daltónico, porque el cronómetro dice el número.

### 6.2 El botón ✓

Círculo de **88 px** (**25 mm** físicos), esquina inferior izquierda, verde `#15803D`.

**Es ✓ y no ✕ por una razón que cuesta dinero.** El símbolo ✕ significa *cancelar* en todos los sistemas del mundo. Un cocinero nuevo, apurado, lee el símbolo antes que la etiqueta — y en Leña cancelar genera merma con costo. La ✓ ocupa el mismo lugar, el mismo tamaño y el mismo gesto, sin la ambigüedad.

**El menú `⋮` guarda lo secundario** y evita el toque accidental en lo que no se deshace:
- **No hay pastor** → marca el producto no disponible (RF-F-10)
- **No puedo prepararla** → cancela la línea, **sin merma** (RF-F-13, RF-F-14)
- Ver detalle

### 6.3 Comanda que regresa (RF-E-7)

El cliente pidió más. La comanda **reaparece** y suena la alerta.

```

│  ┌─────────────────────────────┐  │

│  ~~3× Pastor~~          servido   │  ← gris, tachado

│   ╭─────╮                         │
│   │  ✓  │                    ⋮    │
│   ╰─────╯                         │
```

**Lo ya servido se tacha y se agrisa; lo nuevo se destaca.** El cocinero ve de un vistazo qué falta hacer sin volver a preparar lo que ya salió.

**Y el cronómetro se reinicia para lo nuevo (0:12), no para la comanda.** Lo que se mide es la espera del cliente por *este* platillo. Conservar 8:32 pintaría la tarjeta de rojo por comida que ya se entregó, y el rojo dejaría de significar algo.

Esto **no requiere lógica especial**: sale de la proyección de estado por línea (`05` §4.3). Las líneas en `lista` se tachan, las `pendiente` se destacan. La interfaz solo dibuja lo que el modelo ya sabe.

### 6.5 Sonido

| Evento | Sonido | Por qué |
|---|---|---|
| Comanda nueva | Campana doble, 800 Hz | Corta el ruido de la plancha |
| Comanda que regresa | Campana triple ascendente | **Distinto** de la nueva: no es lo mismo |
| Cancelación | Tono grave, 300 Hz | Grave = malas noticias, sin verlo |
| Umbral rojo | Tic discreto, una vez | Avisa sin volverse ruido de fondo |

**Sonidos distintos por evento, no un "bip" para todo.** El cocinero tiene las manos en el trompo y la vista en la carne: **el sonido debe decir qué pasó sin obligarlo a voltear.** Un solo bip lo obliga a mirar cada vez, y eso cuesta segundos en cada comanda.

**Volumen ajustable y prueba de sonido en ajustes.** Una taquería en hora pico es más ruidosa que una oficina, y un sonido que no se oye no existe.

### 7.1 Merma y cancelaciones — el control antifraude

```
┌──────────────────────────────────────────────────────────────────┐
│  MERMA Y CANCELACIONES              Julio 2026 ▾    [Exportar]   │
├──────────────────────────────────────────────────────────────────┤
│  Merma total    Por cancelación    % de ventas    Tendencia      │
│    $4,280            $3,940           1.4%        ▼ 22%          │
├──────────────────────────────────────────────────────────────────┤
│  POR MESERO                                                      │
│  Mesero    Comandas   Canceladas   Tasa    Merma      vs. equipo │
│  ─────────────────────────────────────────────────────────────── │
│  Carlos      1,240        18       1.5%    $1,120      —         │
│  Ana         1,180        21       1.8%    $1,340      —         │
│  Luis          890        62       7.0%    $1,480    ⚠ 4.2×      │
├──────────────────────────────────────────────────────────────────┤
│  ⚠️  Luis cancela 4.2× más que el promedio. Revisar.             │
└──────────────────────────────────────────────────────────────────┘
```

**Esta tabla es la mitigación completa de T1 y cuesta una consulta SQL.** El fraude interno no se ve en el evento aislado —cancelar una comanda es normal, pasa todos los días— sino en el **patrón**: un mesero con 4× la tasa de sus compañeros. La columna "vs. equipo" hace visible lo que 62 eventos sueltos esconden.

**Y por eso el control es detectivo y no preventivo** (`07` §10): pedir autorización para cada cancelación paralizaría el piso en hora pico y los meseros buscarían cómo rodearlo. Un sistema rodeado no audita nada. Esta tabla, revisada cada mes, disuade casi igual y no estorba a nadie.
