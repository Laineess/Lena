## 1. Restricciones que definen el diseño

Estas son las fuerzas reales del problema. Toda decisión de este documento se justifica contra alguna de ellas.

| # | Restricción | Origen |
|---|---|---|
| R1 | El servicio no puede detenerse si se cae el internet | Operación en taquería, ISP no confiable |
| R2 | El flujo crítico es **mesero → cocina**: dos dispositivos distintos | Visión, actores |
| R3 | Trazabilidad completa del ciclo de vida de cada orden | Visión §2 |
| R4 | Multi-sucursal desde el diseño, 1 sucursal en producción | Visión §3, confirmado con el negocio |
| R5 | Escala mínima: ~4 dispositivos concurrentes por sucursal | Confirmado con el negocio |
| R6 | Un solo desarrollador | Realidad del proyecto |
| R7 | Fase 2 (recomendación de compra de insumos) necesita historial granular desde el día 1 | Ver §7 |
| R8 | El dinero histórico es inmutable: cambiar un precio hoy no altera un ticket de ayer | Requisito contable |

**R5 es tan importante como R1.** A esta escala, sobre-diseñar cuesta más que el problema que resuelve. No hay Redis, ni colas externas, ni microservicios, ni Kubernetes. Un Postgres y un proceso de Node bastan y sobran.

## 3. Decisiones (ADR)

### ADR-001 — Stack: TypeScript self-hosted sobre VPS propio

**Estado:** Aceptada

**Contexto:** Un solo desarrollador, presupuesto mínimo, VPS ya disponible, necesidad de SQL analítico para Fase 2 y de correr el backend dentro de la sucursal en Fase 3 (ver ADR-004).

**Decisión:**

| Capa | Elección |
|---|---|
| Cliente | React 19 + TypeScript + Vite, PWA (`vite-plugin-pwa`) |
| UI | Tailwind CSS + shadcn/ui |
| Estado servidor | TanStack Query |
| Estado local / outbox | Dexie (IndexedDB) |
| API | Node 22 + Fastify + TypeScript |
| Acceso a datos | Drizzle ORM |
| Base de datos | PostgreSQL 16 |
| Tiempo real | WebSocket nativo + Postgres `LISTEN/NOTIFY` |
| Reverse proxy / TLS | Caddy |
| Despliegue | Docker Compose sobre VPS propio |

**Alternativas consideradas:**

- **Supabase (BaaS).** Ahorraba ~3-4 semanas: Auth, Realtime y RLS ya resueltos, y RLS mapea muy bien al aislamiento por sucursal. Rechazada porque el nodo en sucursal de ADR-004 exigiría self-hostear Supabase entero, que es mucho más pesado que correr nuestra propia imagen. El ahorro de hoy se pagaba con intereses en Fase 3.
- **Next.js + Vercel.** Rechazada por incompatibilidad de fondo: Next es SSR-first y los Server Actions no existen sin red. Construir un PWA offline-first encima es pelear contra el framework todo el proyecto. Es la opción popular y la equivocada para este caso.
- **CouchDB / PouchDB.** Su replicación multi-master resuelve el sync de fábrica y fue tentadora. Rechazada por R7: es un almacén de documentos y las agregaciones financieras y el motor de recomendación de Fase 2 son SQL analítico puro. Habría obligado a mantener Postgres en paralelo — dos bases, dos verdades.

**Consecuencias:**
- Escribimos nosotros: autenticación, tiempo real y sincronización. Es el costo real de esta decisión.
- Un solo lenguaje de punta a punta; tipos compartidos entre cliente y servidor.
- Costo de operación ≈ el VPS que ya pagas.
- Cero lock-in.

### ADR-002 — El ciclo de vida de la comanda es un log de eventos, no un campo mutable

**Estado:** Aceptada

**Contexto:** R1 + R2 + R3. Con dispositivos escribiendo offline, los `UPDATE` concurrentes sobre la misma fila son la fuente número uno de conflictos de sincronización.

**Decisión:** El estado de una comanda **no** se guarda con `UPDATE comanda SET estado = 'listo'`. Se registra un evento append-only:

```sql
INSERT INTO comanda_evento (id, comanda_id, tipo, actor_id, hlc, ...)
```

El estado visible se calcula plegando los eventos, y se **cachea** en `comanda.estado` como proyección de solo lectura, siempre recomputable desde el log. El log es la verdad; la proyección es conveniencia.

**Por qué esto resuelve tres problemas de una vez:**

1. **Los INSERT no chocan.** Dos dispositivos offline generando eventos nunca producen conflicto de escritura. Se elimina la clase de bug más difícil del sistema por construcción, no por cuidado.
2. **R3 sale gratis.** La trazabilidad que pide la visión *es* el log: quién, qué, cuándo, en orden. No es trabajo extra; es el mismo trabajo.
3. **Idempotencia.** El ID del evento lo genera el cliente, así que reintentar un envío es seguro por definición. Crítico con red intermitente.

**Consecuencias:**
- Leer el estado actual requiere la proyección; el log solo no sirve para consultas rápidas. Hay que mantener ambos consistentes (se hace en la misma transacción).
- La tabla de eventos crece siempre. A ~200 comandas/día × ~8 eventos ≈ 1,600 filas/día ≈ 600k/año. Postgres ni se despeina. No requiere particionado en años.
- **Los conflictos que quedan son de negocio, no de datos** (cocina marca "listo" mientras mesero marca "cancelado"). Se resuelven con reglas explícitas en la máquina de estados, documentadas en `05. Casos de uso y diagramas de estado`.

### ADR-003 — Identificadores generados en el cliente (UUIDv7) + orden por HLC

**Estado:** Aceptada

**Contexto:** Un mesero sin red debe poder crear una comanda. Si el ID lo asigna la base, no puede.

**Decisión:**
- **Llaves primarias: UUIDv7**, generadas en el dispositivo. Son ordenables por tiempo, así que no sufren la fragmentación de índice de UUIDv4.
- **Orden entre eventos: Hybrid Logical Clock (HLC)**, no `timestamp` puro. Un HLC combina reloj físico + contador lógico + ID de nodo.
- **Folio legible (`#42`): lo asigna el servidor al sincronizar**, no el cliente. Dos meseros offline no pueden coordinar una secuencia sin colisionar. La comanda vive con folio `null` hasta que sincroniza, y la UI muestra un identificador temporal mientras tanto.

**Por qué HLC y no `created_at`:** las tablets tienen el reloj mal puesto. Siempre. Un `timestamp` de cliente puede venir del futuro o del pasado y romper el orden de eventos de una misma comanda — por ejemplo, "entregada" antes que "lista". El HLC garantiza orden causal aunque los relojes mientan.

**Consecuencias:** hay que implementar HLC (es ~60 líneas) y la UI debe tolerar comandas sin folio.

### ADR-004 — Offline por niveles: diseñar para sucursal, desplegar por dispositivo

**Estado:** Aceptada

**Contexto:** R1 y R2 juntos. "Offline" tiene dos significados muy distintos y muy distinto costo.

**El problema real:** si cae el internet y no hay nada *dentro* de la sucursal que conecte los dispositivos, la comanda del mesero se encola en su tablet y **la cocina nunca la ve**. Eso no es offline-first; es el problema del papel con pasos extra.

**Decisión — dos niveles:**

| | **Nivel 1 — Offline de dispositivo** | **Nivel 2 — Offline de sucursal** |
|---|---|---|
| Hardware extra | Ninguno | Mini PC en sucursal (~$3,000-4,500 MXN) |
| Al caer el ISP | Mesero sigue capturando; corte de caja correcto; cocina se degrada a coordinación verbal | Todo el flujo funciona igual que siempre |
| Qué se pierde | Coordinación digital con cocina durante la caída | Nada; solo los reportes centrales se retrasan |
| Fase | **MVP** | Fase 3 |

**MVP despliega Nivel 1. La arquitectura se diseña para Nivel 2 desde hoy.**

**Por qué es defendible empezar en Nivel 1:** durante una caída, el mesero sigue capturando en la tablet, no se pierde una venta, y el corte de caja al cierre sale correcto. **El dinero sigue bien.** Lo único que se degrada es la coordinación con cocina, que vuelve al proceso que ya usan hoy. Se pierde una mejora; no se pierde la operación.

**Y por qué el salto a Nivel 2 no será un rewrite:** el nodo de sucursal corre **la misma imagen Docker** que el VPS y habla **el mismo protocolo de sync** (ADR-005). Las tablets solo cambian de URL base. Es un cambio de despliegue y configuración, no de arquitectura. Esta es la razón principal por la que se eligió ADR-001 sobre Supabase.

### ADR-005 — Sincronización: outbox + pull incremental por cursor

**Estado:** Aceptada

**Decisión:** protocolo simétrico en dos direcciones, sin dependencias externas.

**Push (dispositivo → servidor)**
1. Toda escritura local va primero a la tabla `outbox` de Dexie y se aplica de inmediato al estado local (UI optimista, 0 ms de espera).
2. Un worker drena la outbox: `POST /sync/push` con el lote de eventos.
3. El servidor los inserta con `ON CONFLICT (id) DO NOTHING` → **idempotente**. Reintentar un lote nunca duplica.
4. Al confirmar, el evento se marca sincronizado en la outbox.

**Pull (servidor → dispositivo)**
1. Cada evento del servidor recibe un `seq bigserial` monótono.
2. El dispositivo guarda su último `seq` (cursor) y pide `GET /sync/pull?desde={cursor}`.
3. El servidor devuelve solo eventos de **su sucursal** posteriores al cursor.
4. En caliente, el WebSocket empuja los eventos nuevos al instante; el pull por cursor es la red de seguridad al reconectar.

**Por qué `seq` y no `hlc` para el cursor:** el HLC ordena causalmente entre dispositivos, pero no es denso ni monótono global. El `bigserial` del servidor sí, y eso es justo lo que necesita un cursor de paginación. Los dos relojes coexisten y sirven a propósitos distintos: **HLC ordena, `seq` pagina.**

**Tiempo real:** el API hace `NOTIFY` en Postgres al insertar; los procesos suscritos con `LISTEN` reenvían por WebSocket a los dispositivos de esa sucursal. A 4 dispositivos por sucursal (R5), esto es de sobra y evita meter un broker.

**Consecuencias:** la UI debe distinguir tres estados por comanda — *local*, *enviando*, *confirmada* — y mostrarlo. El mesero necesita saber si la cocina ya la vio.

### ADR-006 — El dinero histórico es inmutable: snapshot en la línea de comanda

**Estado:** Aceptada

**Contexto:** R8. El administrador puede cambiar precios, renombrar platos y darlos de baja (Visión §3).

**Decisión:** `comanda_detalle` guarda **copia** de `precio_unitario` y `nombre_producto` al momento de la venta, además del `producto_id` para trazabilidad. El total de la comanda **nunca** se recalcula desde el catálogo vivo.

**Corolarios obligatorios:**
- **Baja de producto = baja lógica** (`activo = false`). Un producto referenciado por historial jamás se borra físicamente. La visión ya lo pedía; aquí está el motivo técnico.
- Los cambios de precio se registran en `producto_precio_historial` (append-only) para auditoría.

**Por qué:** sin snapshot, subir el precio del taco un martes reescribe los ingresos de todos los martes anteriores. Los reportes históricos mienten y el motor de Fase 2 aprende de datos falsos.

### ADR-007 — Autenticación de dos velocidades

**Estado:** Aceptada

**Contexto:** un mesero en plena hora pico no teclea una contraseña fuerte en una tablet compartida. El administrador sí necesita seguridad real sobre datos financieros.

**Decisión:**
- **Mesero y Cocina:** PIN numérico por usuario, único dentro de su sucursal, con el dispositivo previamente registrado y vinculado a esa sucursal. El PIN autentica *a la persona*; el dispositivo registrado autentica *al lugar*.
- **Administrador:** email + contraseña fuerte + sesión corta.
- Hash con Argon2id en ambos casos. Rate limiting agresivo en PIN.

**Por qué el PIN no es un agujero:** solo es válido desde un dispositivo registrado, dentro de su sucursal, y no da acceso a nada financiero. La superficie de un PIN robado es "alguien crea comandas falsas en tu taquería estando físicamente ahí" — un riesgo operativo, no una brecha de datos. El detalle vive en `07. Requisitos de seguridad`.

## 4. Estructura del proyecto

Monorepo, tipos compartidos entre cliente y servidor. Es la ventaja principal de haber elegido un solo lenguaje.

```
lena/
├── apps/
│   ├── web/            # PWA React (meseros, cocina, admin)
│   └── api/            # Fastify + WebSocket
├── packages/
│   ├── shared/         # Tipos, máquinas de estado, HLC, validadores Zod
│   └── db/             # Esquema Drizzle + migraciones
├── docker-compose.yml
└── Docs/
```

`packages/shared` es donde vive la lógica que **no puede divergir** entre cliente y servidor: las transiciones de estado válidas y el cálculo de totales. Si el cliente y el servidor no concuerdan en si una transición es legal, el sync produce estados imposibles. Una sola definición, dos consumidores.

## 5. Flujo crítico: comanda de mesero a cocina

```
Mesero (tablet)                 Servidor                  Cocina (pantalla)
     │                             │                             │
  crea comanda                     │                             │
  UUIDv7 local                     │                             │
     │                             │                             │
  UI actualiza (0 ms) ◄────────────┼─────────────────────────────┤
     │                             │                             │
  outbox ──► POST /sync/push ─────►│                             │
     │                        INSERT evento                      │
     │                        (idempotente)                      │
     │                             │                             │
     │                          NOTIFY                           │
     │                             ├──── WebSocket ─────────────►│
     │                             │                        aparece
     │◄──── ack ───────────────────┤                             │
  marca "confirmada"               │                             │
```

Sin red, el mesero se queda en el paso 3: la comanda existe, es válida y está encolada. Al volver la red, los pasos 4-7 corren solos y la cocina la ve. Nada se pierde; solo llega tarde.

## 6. Qué NO está en esta arquitectura (y por qué)

Decisiones de omisión, tan importantes como las de inclusión:

| Omitido | Razón |
|---|---|
| Redis / broker de mensajes | R5. `LISTEN/NOTIFY` cubre 4 dispositivos con margen de sobra |
| Microservicios | R6. Un dev, un dominio, un deploy |
| CRDTs (Yjs, Automerge) | Resuelven edición colaborativa de texto. Un log de eventos append-only ya elimina los conflictos que tenemos, sin la complejidad |
| Kubernetes | R5 + R6. Docker Compose sobrará durante años |
| Impresión de tickets | Fuera del MVP por decisión de alcance |
| Facturación CFDI | Fuera del MVP por decisión de alcance |
| Tabla `organizacion` / multi-tenant real | R4. Un despliegue = un negocio. `sucursal_id` basta |

## 7. Ganchos para Fase 2 (inventario y recomendación de compra)

El modelo de insumos del negocio **no es de recetas ni escandallos**. Es de conteo diferencial:

```
consumo_del_día = conteo_apertura + compras_del_día − conteo_cierre
```

Sin recetas no existe un "consumo esperado" contra el cual comparar. Pero el sistema puede **aprender la receta implícita** correlacionando ventas históricas contra consumo derivado de conteos: si los sábados se venden 200 tacos y se consumen 8 kg de carne, el ratio se deduce de los datos sin que nadie capture una receta.

La recomendación de compra sale de ahí:

```
compra_recomendada = consumo_previsto_hasta_próxima_entrega
                   + stock_seguridad
                   − stock_actual
```

Con pronóstico de ventas por **día de la semana** (un lunes y un sábado no se parecen en nada). Es SQL y estadística simple — media móvil y regresión lineal. Cero machine learning.

**La consecuencia arquitectónica es hoy, no en Fase 2 (R7):** ese motor necesita historial. Si el MVP no guarda **cada venta con producto, cantidad, timestamp y sucursal** desde el primer día, la Fase 2 arranca con cero datos y no puede recomendar nada durante meses. Por eso el modelo de datos incluye las tablas de Fase 2 desde ahora, aunque la UI no las use todavía.

Esto también refuerza ADR-006: si los precios históricos se reescriben, el motor aprende de datos falsos.

## 8. Riesgos técnicos

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Bugs en el sync propio | Alto — datos corruptos o duplicados | ADR-002 + ADR-003 los eliminan por construcción (INSERT idempotentes con ID de cliente), no por cuidado. Suite de pruebas de sync con red simulada |
| Reloj de tablet desfasado | Medio — eventos fuera de orden | HLC (ADR-003) |
| Crecimiento del log de eventos | Bajo — ~600k filas/año | Índices por `comanda_id` y `seq`. Particionado si algún día pasa de ~50M filas |
| VPS único = punto único de falla | Medio | Backups automáticos diarios de Postgres + retención 30 días. Nivel 2 (ADR-004) también lo mitiga |
| Deuda de auth propia | Medio | Argon2id, rate limiting, sesiones cortas. Detalle en `07. Requisitos de seguridad` |
