### 3.2 Swap de 2 GB

```bash
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo "/swapfile none swap sw 0 0" >> /etc/fstab

sysctl -q vm.swappiness=10
echo "vm.swappiness=10" >> /etc/sysctl.conf
```

**`swappiness=10` es deliberado:** el swap es una **red de seguridad**, no memoria de uso rutinario. Con 60 (el default) el kernel paginaría por costumbre y el disco sufriría. Con 10, solo pagina cuando de verdad aprieta.

**Por qué el swap era lo primero:** sin él, un pico de cualquier proceso invoca al OOM killer, que elige víctima por tamaño de RSS — y la víctima habría sido `mysqld` (436 MB), llevándose `portal_escolar` de corbata. **El swap se puso para proteger los proyectos existentes, no para Leña.**

**Verificado que los proyectos siguieran vivos antes de continuar:** 302/404/404, idénticos a la línea base.

### 3.3 Ajuste de memoria de MySQL

**Archivo nuevo, no se editó ninguno existente** — así revertir es borrar un archivo:

`/etc/mysql/mysql.conf.d/zz-lena-memoria.cnf`

```ini

innodb_buffer_pool_size = 64M     # cachea 3 MB de datos; 128M era 40x de más
innodb_buffer_pool_instances = 1

read_rnd_buffer_size = 256K

table_open_cache = 200
```

**Validado ANTES de reiniciar** — esto elimina el riesgo de "MySQL no arranca":

```bash

```

Reinicio con reversión automática:

```bash

# si no responde en 30 s → rm del .cnf + restart + verificar
```

**Resultado:**

| | Antes | Después |
|---|---|---|
| `mysqld` RSS | **436 MB** | **154 MB** |
| Arranque | — | **1 segundo** |
| `portal_escolar` | 25 tablas, 2.1 MB | 25 tablas, 2.1 MB ✓ |

InnoDB es *crash-safe* y `systemctl restart` cierra limpio. El único riesgo real era un error de sintaxis, y `--validate-config` lo descartó antes de tocar el servicio.

## 4. Verificación

### 4.1 Control antifraude (RS-U-1, amenaza T1)

**Esta es la prueba que no se puede omitir.** Conectado **como `lena_app`** — el rol que usará el API:

```bash
APP_PASS=$(grep "^DATABASE_URL_APP=" .env | sed -E "s|.*://lena_app:([^@]*)@.*|\1|")
docker exec -e PGPASSWORD=$APP_PASS lena-db psql -U lena_app -h 127.0.0.1 -d lena -c "..."
```

| Prueba | Esperado | Resultado |
|---|---|---|
| `SELECT FROM comanda_evento` | permitido | ✅ permitido |
| **`DELETE FROM comanda_evento`** | **denegado** | ✅ **permission denied** |
| **`UPDATE comanda_evento`** | **denegado** | ✅ **permission denied** |
| `DELETE FROM producto_precio_historial` | denegado | ✅ denegado |
| `DELETE FROM merma_producto` | denegado | ✅ denegado |
| `DELETE FROM merma` | denegado | ✅ denegado |
| `DELETE FROM pago` | denegado | ✅ denegado |
| **`DELETE FROM mesa`** (control) | **permitido** | ✅ **permitido** |

**La última fila es la que valida la prueba entera.** Sin ella, "todo denegado" podría significar simplemente que `lena_app` no tiene permisos de nada — y eso no sería append-only, sería un rol roto. Que `mesa` **sí** permita `DELETE` demuestra que el `REVOKE` es quirúrgico y funciona.

Permisos declarados sobre `comanda_evento`: **`INSERT`, `SELECT` y nada más.**

### 4.3 El índice parcial que hace posible el offline (ADR-003)

| Prueba | Resultado |
|---|---|
| **3 comandas sin folio (`NULL`) coexisten** | ✅ **permitido** |
| Dos comandas con folio `42` en la misma sucursal | ✅ rechazado |

**La primera fila es el offline entero.** Si un `UNIQUE` normal tratara los `NULL` como iguales, dos meseros sin red no podrían crear comandas simultáneas y **el modo offline no existiría**. El índice parcial `WHERE folio IS NOT NULL` es lo que lo permite.

### 4.4 Zona horaria (RES-4) — el bug demostrado

Primer intento: **la prueba no probó nada.** El contenedor ya tiene `TZ=America/Mexico_City`, así que `::date` acertaba por accidente. Repetida forzando sesión UTC — lo que haría un API mal configurado:

```sql
SET TIME ZONE 'UTC';
SELECT (TIMESTAMPTZ '2026-07-11 20:00:00-06')::date,                                -- sin conversión
       (TIMESTAMPTZ '2026-07-11 20:00:00-06' AT TIME ZONE 'America/Mexico_City')::date;  -- como la vista
```

Venta del **sábado 11 de julio, 8:00 PM** hora de México:

| | Fecha | Día ISO | |
|---|---|---|---|
| Sin conversión | `2026-07-12` | **7 = domingo** | ❌ |
| **Con `AT TIME ZONE`** | `2026-07-11` | **6 = sábado** | ✅ |

**El bug es real.** Sin la conversión explícita de la vista, las ventas del sábado por la noche se contabilizan en domingo y el pronóstico por día de la semana de la Fase 2 (RF-M-2) queda inservible.

**Y la lección de método:** la primera prueba pasó por la razón equivocada. Una prueba que no puede fallar no prueba nada.

```bash
# o restaurar la config completa:
cp -a /root/respaldos-pre-lena/etc-mysql-20260715_164944/. /etc/mysql/
```

**Datos de MySQL (solo si algo saliera mal):**
```bash

```

**Swap:**
```bash
swapoff /swapfile
sed -i '/^\/swapfile/d' /etc/fstab
rm /swapfile
```

**Docker:**
```bash
apt-get purge -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
rm /etc/apt/sources.list.d/docker.list
```

**`portal_escolar` y `pretty_faces` no tienen ningún respaldo automático.** Ni antes de este despliegue ni ahora. Si el disco del VPS muere, se van completos.

**No es un pendiente de Leña** — existía antes y es independiente de este proyecto. Se documenta aquí porque salió a la luz durante la inspección, y porque un servidor con dos sistemas en producción sin respaldos es un riesgo mucho mayor que cualquier cosa que Leña pueda causar.

Se resuelve con un cron y ~20 minutos (el patrón está en `11. Despliegue en VPS` §8). **Es decisión del dueño**, no de este proyecto.

## 10. Lecciones

**La guía se escribió para un servidor que no existía.** `11. Despliegue en VPS` asumía una máquina dedicada; la real tiene dos proyectos en producción, nginx público y acceso por root. Tres de sus pasos habrían causado un incidente. **Inspeccionar antes de ejecutar no fue precaución: fue la diferencia entre desplegar y romper.**

**El problema no era el que parecía.** Se entró a instalar Postgres preocupado por la falta de RAM. El verdadero problema era MySQL cacheando 3 MB con un buffer de 128 MB y `performance_schema` encendido. Medir antes de optimizar convirtió "no cabe" en "sobran 225 MB".

**Una prueba que no puede fallar no prueba nada.** La primera prueba de zona horaria pasó porque el contenedor ya tenía la TZ correcta — habría pasado igual con la vista rota. Solo forzando sesión UTC se demostró que la conversión hace algo.

**Y el control de la prueba importa tanto como la prueba.** Verificar que `lena_app` **no** puede borrar el log no significa nada por sí solo: un rol sin permisos daría el mismo resultado. Comprobar que **sí** puede borrar de `mesa` es lo que demuestra que el `REVOKE` es quirúrgico.
